# Google OAuth approval and recovery (#1140)

**Draft pilot only. OFF in production.** Supabase may automatically attach verified matching-email Google identities upstream even without a PMS linking action. A Supabase UID, JWT, or matching Gmail alone must never authorize access to an existing PMS student.

## Enforcement and data minimization

In Supabase mode, PMS checks current Supabase Admin identities on every potentially authorized API call, even when the JWT's provider metadata is stale. If a Google identity is present or advertised, an existing bound `User.authId`, **exactly one** current Google identity, an existing student role, `GOOGLE_OAUTH_APPROVAL_ENABLED=true`, and the latest **approved** database event matching `(PMS User.id, Supabase UID, Google identity ID)` are all required. Missing store, Admin outage, unapproved/revoked/wrong/duplicate identity, unknown UID or email-only candidate fail closed. The old `GOOGLE_OAUTH_APPROVED_IDENTITIES` environment allowlist is **ignored**, not a release control. No student record, account linkage, role or enrollment is created or rewritten by approval.

`pms_auth_security` is a **SQL-managed restricted schema outside Prisma's public models**. A migration creates a short-lived `google_link_intent` and append-only `google_identity_approval_event` with actor, target, exact IDs, restricted evidence-reference, reason and timestamp. Row-level security is on; the schema/tables are revoked from PUBLIC/anon/authenticated/service_role, and `bun run --cwd apps/backend db:security:verify` checks this inventory, append-only trigger, RLS and Data API isolation. The server's own DB role must be able to access the restricted schema. Do not expose it through Supabase's Data API/exposed schemas. Event rows cannot be edited or deleted; revocation is a new event, effective on the next protected request.

## Server-attested linking and operator approval

1. In a disposable **separately migrated and seeded PMS database** with a separate Supabase Auth project, configure backend `AUTH_MODE=supabase`, matching `SUPABASE_URL`, `SUPABASE_JWKS_URL`, server-only `SUPABASE_SERVICE_ROLE_KEY`, `DATABASE_URL`, and `GOOGLE_OAUTH_APPROVAL_ENABLED=true`. Set frontend `NEXT_PUBLIC_GOOGLE_PILOT_ENABLED=true` only for this isolated preview. Both Google flags stay false in production. An OAuth redirect to `/google-link/callback` must be on the **test** Supabase redirect allow-list. Never put credentials or access tokens in chats, PRs, screenshots or source control.
2. Start with an already-provisioned, active, **nonprivileged** PMS student with official student ID and confirmed email/password identity. The student explicitly consents on `/connect-google`, provides their **existing PMS password**, and the backend verifies it directly against the same Supabase UID before recording one 30-minute intent. Frontend also checks that the refreshed UID is unchanged, then calls `linkIdentity`. An unauthorized/upstream auto-linked Google identity without a recent intent cannot receive approval through the API.
3. `/google-link/callback` is intentionally **outside the PMS shell**. It checks original UID vs returned authenticated UID, confirms exactly one Google identity, and displays *pending independent approval*. It does not enter the protected PMS UI or claim that linking equals approval.
4. An independent **global administrator** verifies the existing official student record, student consent, and the exact current provider identity using restricted institution-approved procedures, then stores a ticket/evidence reference **without PII or secrets**. The operator reauthenticates with their existing password. POST `/api/auth/google/approve` with `targetUserId`, `authUid`, `googleIdentityId`, `evidenceReference`, `reason`, `adminPassword`, and all three `studentRecordVerified`, `directConsentVerified`, `providerOwnershipVerified` true. The backend rechecks exact live Google ID, original bound PMS User, active nonprivileged student, and an unconsumed 30-minute password-verified intent; consumes intent atomically and appends decision. Operator self-approval, missing evidence and replay fail closed. Restrict API access and logging; never send passwords as query strings.
5. POST `/api/auth/google/revoke` with matching exact identifiers, restricted evidence reference, reason and operator password (plus required declarations while the pilot endpoint is in draft); the latest revocation blocks Google *and existing password sessions while Google remains linked*. A frontend flag change alone cannot undo Supabase upstream identity linking. A person losing Google access needs supervised original-account ownership verification, removal of unintended provider identity via authorized Supabase procedures, session revocation and a fresh password login. Verify canonical User/Student IDs and academic records remain unchanged. Record action/ticket securely; never delete audit events.

`/api/auth/google/link-intent`, `/approve`, `/revoke` are behind the existing PMS authentication middleware and backend feature flag. The password/secret is not persisted or logged by the feature. Operator evidence declarations record what a human checked; they do **not** independently prove off-platform identity evidence. The same administrator must not be the student. Recoveries where an unwanted Google identity blocks PMS login are manual, independently verified and **not yet hosted-UAT validated**.

## Release evidence and blockers

The isolated hosted Auth browser experiment verified **explicit** Google linking, signed-out Google login and restored password sign-in for one disposable operator-owned identity. It did **not** test first-login automatic same-email linking or a live PMS backend. Synthetic CI tests use local mock Supabase Admin/JWKS with disposable seeded PostgreSQL and do not replace real hosted tests.

Before merge: finish and demonstrate real hosted first-time automatic linking, JWT refresh, account-switch/replay, intent expiry, operator approval/revocation/recovery, failure of email-only impersonation, second-student denial, password fallback, and rollback. Connect only **synthetic PMS records** to separate hosted test Auth. Then complete one consenting nonprivileged student's controlled preview UAT and parent merged #1143's acceptance/security gates. Keep production Google provider and frontend/backend flags disabled. See [pilot runbook](google-oauth-pilot.md) and [redacted hosted Auth evidence](google-hosted-auth-test-2026-09-16.md).

Read-only production roster aggregates from 16 September 2026 do **not** establish where the registration form's personal Gmail answers were stored. Do not assume `Student.email` is personal Gmail, change official records, or bulk-approve from roster emails.
