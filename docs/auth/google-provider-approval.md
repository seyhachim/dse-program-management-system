# Google OAuth server-side identity approval (#1140)

**Pilot only; off by default.** Supabase [automatically links verified matching-email OAuth identities](https://supabase.com/docs/guides/auth/auth-identity-linking). Google OAuth therefore MUST NOT be treated as proof of ownership of the existing DSE PMS account merely because `auth.users.id` matches. A frontend `/api/auth/me` check does not solve this issue by itself.

## Enforced authorization boundary

When a verified Supabase JWT's `app_metadata.provider` or `app_metadata.providers` advertises Google, the backend independently fetches that UID's identities with the server-side Supabase Admin API. It requires an existing PMS `User.authId`, a student role, **exactly one** Google identity, and an explicit operator-approved `(Supabase UID, Google identity ID)` pair. Missing, malformed, mismatched or duplicated approvals reject every protected API request with 403, even when Supabase itself has linked the identities or a matching roster Gmail exists. The approval lives in the backend environment, not in a frontend flag or a user-editable email field.

For a single-student pilot, set **backend only** `GOOGLE_OAUTH_APPROVED_IDENTITIES` to a JSON object such as `{"<verified-supabase-uid>":"<verified-google-identity-id>"}`. Use the exact identity `id` obtained from an authenticated, authorized administrator's Supabase Auth identity inspection; **do not use an email, Google display name, OAuth client ID or `provider_id` in place of the identity ID**. Keep real identifiers and evidence in restricted operational records, never in PRs, chat, screenshots or client environment variables. Empty/unset config denies all Google logins. Changing or deleting an approval takes effect on the next API request without modifying Student, User, enrollment or academic records. Restrict backend environment access; record operator, time, verified institutional identity, approval and revocation in the university's restricted change log.

Before approving the pair, an authorized operator must independently verify the student's existing PMS identity and consent, confirm that the Google identity was intentionally connected by the student, and check the canonical `User.id`, `User.authId` and `Student.id` have not changed. **Google email equality alone is not sufficient.** If the student's email/password and Google emails match, Supabase may auto-link them before the operator can approve; until approval the backend deliberately denies the Google-linked UID, including its password sessions when the JWT lists Google. Do NOT trial this in the production Auth project with an active student. Test disposable identities in an isolated Supabase project first and document an approved recovery procedure for an unintended link (disable Google provider, verify original account ownership, unlink/revoke the unintended identity through an authorized process, and verify the original account's access). Turning off the frontend flag alone does not remove a linked identity.

This pilot approval prevents a silently auto-linked Google identity from obtaining PMS API access. It does **not** prevent Supabase from linking upstream, restore an account after an unintended link, or prove that hosted OAuth/reauthentication flows have been tested. Owner-controlled negative-path UAT remains mandatory. Future production rollout should replace the operator-managed JSON with durable auditable per-provider approvals and ensure sensitive linking requires recent authentication; don't add all students to an allowlist merely from roster emails.

## Read-only roster audit (16 September 2026)

The connected PMS Supabase project's `public."Student"` has `email`, `userId` and `studentId`, but no dedicated personal Gmail column was found in the database's column metadata. A read-only aggregate query found 113 Student records, 0 missing `Student.email`, only **1** `Student.email` ending in gmail.com/googlemail.com, 7 linked to a PMS User, 105 with no official `studentId`, 0 case-insensitive duplicate Student emails, and 1 linked Student/User email mismatch. The `User` table contains 35 records, 12 with authId and 2 Gmail addresses. These aggregates do **not** establish where the registration form's personal Gmail answers were stored, so do not use `Student.email` as if it were the personal Gmail roster and do not backfill or change any student/academic fields as part of this pilot. Review the registration form's original source and its consent/provenance through an authorized process before any broader onboarding.

## Operator release gate

Verify the backend approval configuration and a pre-approved identity pair in a disposable isolated Auth environment; test a matching-email automatic link without approval (403), wrong UID, wrong Google identity ID, duplicate identities, and unknown/non-student users (403). Verify password recovery and legitimate access for an approved student, logout, cross-student API isolation, and safe rollback. Keep `NEXT_PUBLIC_GOOGLE_PILOT_ENABLED` unset/false in production until the dependent PR #1139 has merged and #1140's full acceptance criteria and a one-student UAT have been met. Do not put secrets or student identifiers in test reports.
