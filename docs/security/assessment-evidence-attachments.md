# Private course assessment evidence — #1366 / #1367

## Scope and operator gate

This draft adds one PDF/JPG/PNG file (up to 5 MiB) or one restricted external reference per evidence revision, for finalized individual results, shared group scores and individual components. No grade changes. Replacements create new immutable revisions. Stored files are sensitive academic records, never public student portfolio items. A file's SHA-256 records the uploaded bytes, not proof of student authorship or assessment validity. Lecturer and independent coordinator must verify marked work. Shared group scores use one artifact per group/assessment source; individual components are separate evidence records and never inferred from derived student grades. Other provider links remain future work.

Uploads default to disabled. Do not enable them or use real student evidence before isolated hosted staging, security review, retention approval and CI.

## Isolated staging setup

1. Use a separate staging Supabase project with no production data, backend-only service credentials and an explicitly private bucket named `assessment-evidence-private`. Set the bucket limit to 5242880 bytes and MIME allowlist to application/pdf, image/jpeg, image/png. Never reuse public news or leave-letter buckets.
2. Inspect existing storage.objects policies; no public/client policies may authorize this bucket, including broad policies written for other buckets. A restrictive denial for anon/authenticated for this bucket (USING and WITH CHECK) is recommended where compatible with the isolated project. Test direct read/list/write/update/delete with anonymous and authenticated tokens; backend service role is the only storage writer. Do not issue signed upload URLs.
3. Install ClamAV clamscan on the backend runtime and maintain current signature databases via a trusted update process. Test clean samples, EICAR test signature, encrypted content, scanner failure and timeout. Configure ASSESSMENT_EVIDENCE_CLAMSCAN_READY=true only after checking signatures and runtime; set ASSESSMENT_EVIDENCE_UPLOADS_ENABLED=true only after all gates pass. No scanner or bucket credentials in frontend/public env. Backend rejects files when disabled or scanner fails. Signature checks are format screening, not complete file sanitization. Never render uploaded PDF or images inline.
4. Deploy additive migrations on isolated staging. Verify RLS and Data API grants for AssessmentEvidenceRevision. Test exact offering/version/assessment/result scope, separate lecturer/coordinator accounts, cross-programme denial, no self-review, stale result after correction, immutable history and concurrent upload conflict. Verify storage path omitted from ordinary DTOs and signed download links expire after 60 seconds. A signed URL is a short-lived bearer capability and may still work until expiry after role revocation; do not send it via logs or chat. Verify no public URL works.
5. Confirm frontend Course Delivery → Assessment Evidence at desktop and mobile widths; select representative result, upload scanned synthetic PDF, submit, review, request changes, replace/retain attachment and verify history. Check separate group and individual-component populations, locked membership, correction-driven stale status, no eligible marks, storage disabled and expired download states.
6. Check real storage capacity, upload limits, quota and rate-limiting under synthetic load. The per-process scanner concurrency limit is not a distributed rate limit. Confirm scanner resource bounds and timeout on hosting platform before enabling uploads.

## Retention and failure handling

Original versions are kept for audit; a new draft does not delete old evidence. Do not enable until DSE/RUPP approves access, retention/deletion and legal-hold rules. This branch does not implement a retention purge or external export. Failed known-rollback uploads attempt private object removal; ambiguous commit/upload outcomes may leave private objects. Reconcile objects against every historical attachment objectKey after an agreed grace period, using a read-only report first; delete only confirmed unreferenced objects with authorization, never delete referenced revisions. Monitor quota without logging student data, filenames, object paths, tokens or document contents.

## Verification status

Unit tests, synthetic HTTP authorization and metadata-only DB lifecycle regression are in CI. No real-storage upload, antivirus, browser UAT or staging deployment has been performed by this implementation. Live storage smoke and staging security review are mandatory release gates. No production bucket, credentials, migration or deployment are created by this PR.

## Programme coordinator coverage

The Course Delivery programme evidence dashboard lists only programmes allowed by the caller's scoped leadership roles and QA management permission. Filter by term and course code/title; page through offerings, inspect approved specification readiness, independent population counts and outstanding sample gaps, then open the exact offering/assessment/population. Dashboard summary tiles are page totals, not term-wide totals. The target is the proposed DSE convention of up to three verified samples per population with eligible finalized source marks, not a compliance rating or mandatory AUN-QA sample count. Assessment applicability and exceptions (e.g. attendance-only assessments) require programme policy and are not automated. No eligible marks is not ready. Correction changes invalidate verification for the affected source; previously verified revisions remain historical. Dashboard does not return student identities, source marks or links. Group/source revision snapshots retain locked member enrollment IDs, separate adjusted individual scores, criterion marks and correction provenance. Validate coordinator-only access, no identity leakage, query latency, pagination and browser drill-down in staging.
