# Exam variant management — Phase 2B (#1371)

Stacked on #1373 at 4b0c2cd; #1372 is the domain foundation. Parent #1355, pilot #1281. **Inactive server-only service; not a production release.**

## Contract and decisions

- Factory accepts the Prisma client and a dedicated >=32-byte server-only HMAC key; no default key, env configuration, singleton, route or plugin registration. AuthUser is a trusted authentication-boundary input; strict input schemas reject additional actor, programme or approval fields. Never forward raw request errors or proposal tokens to logs. A future authenticated route must sanitize errors, protect tokens and provision/rotate the dedicated key; signed payload is not encrypted.
- Reload live role assignments, active roles and permissions within transactions. Only an assigned primary/co-lecturer with scoped lecturer + offerings:write may prepare/assign. Only scoped coordinator/admin with courses:manage may approve/permit. Global grants accepted only for admin. Reads limited to those two classes. Recheck preparer and ownership at approval. Reviewer distinct from preparer, even for dual-role users. No secretary/student/QA reviewer privilege inheritance.
- Derive programme, course, approved CourseSpec, active individual Exam item, weight, CLOs and offering from authoritative rows. Deliberately conservative exact Exam type until real assessment taxonomy is reviewed; no legacy rubric binding or result reconciliation. Prepared mapping is explicit, one direct/supporting mapping per exact marking-scheme question; maxima and order are loaded, never accepted from client. Recompute both hashes; reject tampering, invalid mapping, stale scope/revision, replay, unknown permissions. New assignments require an Active offering and active student with official ID. Historical exact resolution may read archived marking schemes if the content hash still agrees.
- Proposal is a signed, 30-minute, offering-bound envelope for the reviewer to inspect and approve the exact expected hash. It proves the service issued the mapping under the authenticated preparer, not an external evidence file's validity. Reviewer explicitly attests an opaque moderation reference. No persistent draft queue, rejection/return workflow, evidence-store validation or institutional moderation policy is claimed; Phase 2C must design those with access and retention before activation.
- First approval atomically creates the common configuration if absent, inserts the immutable version and grants the exact preparing offering. Subsequent versions use sequential revisions and identical exam maximum. Another offering requires explicit scoped reviewer permission. No latest/default resolution. Existing DB rows trusted only as persisted records, with hash and scope revalidation.
- All operations use serializable transactions and offering-first/spec locks, assignment row lock, expected revision, explicit evidence/reason and database-generated append-only events. Conflicts fail closed; no auto-retry. No direct audit insertion, no delete, no grade or CLO result mutation. Existing result blocks initial assignment and correction. Historical totals are not recalculated. A legacy writer can still grade without respecting assignment; Phase 3 must implement shared lock/interlock, variant-aware grading, corrections and publication before activation.
